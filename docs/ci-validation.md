# Bounded dependency-aware validation

2026-10-05. The user authorized local resumable commits instead of routine intermediate pushes, one conservative historical CI reuse path, and full main/manual validation. This changes validation orchestration, not statistical contracts, tolerances or results.

## What remains mandatory

`check` and `python` retain their names and read-only permissions. Frontend checks, **full standard unittest discovery**, source validation, and every standalone pipeline outside Stage39 still run. No behavioural test is omitted. No national inference, hosted model cache, whole-run cache or schedule is introduced. Main pushes and `workflow_dispatch` ran full when this stage was written; the last section supersedes that for Stage45/46 on pushes (manual dispatch stays full). PR concurrency cancels only superseded runs in the existing PR/event group. The first PR changing this workflow/selection/registry runs full.

The semantic registry identifies one inspected Stage24 pure archival regeneration method, **kept full because its dependency closure is unregistered**. It explicitly identifies Stage39's bounded saved-conditional compatibility test as behavioural, despite `reproduce` in its name. Classification is based on inspected bodies and source fingerprints, not test names or timings. New tests default to behavioural. Since 2026-10-07, changing or adding a test forces full standalone Stage39 validation only when it is a Stage39 or CI-policy test (amendment at the end of this document). Ordinary `python3 -m unittest discover -s scripts/tests -v` is unchanged. This is a small semantic foundation, not a classification of the whole historical suite.

## The only safe subset: Stage39

The five existing Stage39 `--check` commands remain the unchanged full path. A routine PR can replace those commands with `python3 -m scripts.validate.ci_stage39 --check` only when:

1. The PR base commit and a merge base are available; comparison uses that merge base, with missing/disconnected history forcing full.
2. The reviewed fingerprint matches all prior code, exact Stage39 consumed/protected/output files and Python environment contracts.
3. Prior successful Linux evidence remains intact, including the tested head and completion markers.
4. Every changed path belongs to an explicitly reviewed unaffected scope. Unknown paths, raw/required output changes, shared code, dependency files, CI/registry/checkpoint-policy changes, and changed/new Stage39 or CI-policy tests force full; other test files are reviewed as unaffected (2026-10-07).

The dependency list is deliberately a conservative superset: every Python file in the validated historical tree, exact Stage39 input/preservation contracts and outputs, Python version/requirements, and the deterministic Stage39 report. Reuse also requires the attested Linux x86-64/Ubuntu 24.04/Python 3.12.2 runtime, pinned numerical package versions and runner image `20260927.320.1`; an updated/missing image identity or different runtime forces full. That is deliberately conservative and may limit reuse after image updates. New Stage45 code/output paths are explicitly separate consumers; modifications to previously validated shared helpers still force full. Other unknown/new pipelines are not assumed independent. Unrelated source registrations may conservatively force full; no old consumed-source contract is changed.

The reuse attestation refers to actual successful Linux Verify runs [37275901476](https://github.com/jamesfeng24/nz-election-model-2026/actions/runs/37275901476) and [37275906724](https://github.com/jamesfeng24/nz-election-model-2026/actions/runs/37275906724), head `5283e7c85bab23d31176c2160964672b5e0cca3f`, Python 3.12.2/Ubuntu 24.04.5. The preserved full first-run log is checksummed; dependency hashes were reconstructed from that Git tree. A freshly generated output manifest is **not** evidence that reconstruction previously passed.

The lightweight path checks those exact bytes, consumed/protected sources, construction/evaluation seals, construction signature, all six case/sample/fit/schema contracts, all 48,000 complete fine national vectors, complete candidate-share simplexes/intervals, and present optional runtime-cache hashes. It requires no runtime cache. It does not regenerate candidate draws or claim new independent arithmetic. Missing/stale/corrupt fingerprints fail closed. No registry entry can silently turn an unchecked pipeline into reusable output.

# Frozen-pipeline reuse for Stage45 and Stage46 (2026-10-06)

**Rule:** a frozen pipeline's expensive replay is skipped while its code, consumed inputs and hashes are unchanged; whenever any of them is modified it runs in full once, on the PR that modifies it, and that successful PR run is itself the reference, so the merge's main push, and every later change set, reuse it instead of replaying a second time. Manual dispatch is the explicit full run.

Stage46 alone cost about 38 minutes of every full Linux run (construction 31m24s, evaluation 2m53s, verification 3m21s in main run 37354825431); Stage45 about 4.5 minutes; Stage39 about 3.8. Every future stage inherited that cost although frozen code, inputs and outputs were unchanged. This change lets a **pull request or main push** skip only those expensive `--check` reconstructions when it can prove the validated tree is equivalent, *for that pipeline*, to a main commit whose complete Linux Verify run already executed them successfully. It changes validation orchestration, not statistical code, outputs, thresholds, draw counts, laws or saved artifacts.

## What is replaced, and what always runs

Replaced when proved reusable: Stage45 `construction`, `evaluation`, `mean_audit`, `verification`; Stage46 `construction`, `evaluation`, `verification` (`.github/validation/frozen-pipelines.json` `replacedCommands`). They are replaced by `python3 -m scripts.validate.ci_frozen --check --pipeline stageNN`, which re-proves the recorded selection offline, runs the pipeline's own `verify()` (consumed-input and prior-artifact hash contracts) and parses every committed output JSON. Always run, never replaced: complete `unittest discover` (behavioural tests), source validation, frontend checks, every other historical command, and the cheap Stage45/46 `diagnosis`, `priors`, `estimation`, `numerics`, `report`, `manifest` and `reference` checks (the manifests re-hash every committed output and consumed input; they were run locally with no `.cache` present). `workflow_dispatch` never reuses anything and is the manual full run; `python3 -m scripts.validate.ci_frozen --full` is the equivalent explicit selection. Stage39 keeps its separate original path (`ci_selection.py`), which still treats pushes as full.

## Proof, from Git rather than manifests

A pipeline is reused only if some **attested run** passes all of these; otherwise the pipeline runs in full:

1. Event is `pull_request` or `push` to main. The comparison base is the PR base, or `github.event.before` for a push; a missing, zero or unreachable base is full.
2. The attested commit is an ancestor of the tree under validation, the working tree is clean, and the attested run was a successful `push` or `pull_request` run of that commit (a PR run attests the PR head) whose `python` job executed **every replaced command with conclusion `success`** (a run that itself reused a pipeline is therefore not an attestation for it).
3. Attested runs come from, in this order: the pipeline's durable **pin** (`pipelines.<name>.pin` in the registry: commit, run id, evidence file and its SHA-256, scope fingerprint; checked from Git alone), then, only if the pin does not prove reuse, the newest reachable successful `ci.yml` run (main pushes, pull requests and manual dispatches of main) whose `python` job executed that pipeline's replaced commands, read live from the Actions API with the job token (`actions: read`). See *Durable attestations* below; this replaces the earlier fixed-size recency window and global seed, which let a genuine attestation fall out of discovery. API failure, absence of a token or any parse problem only drops discovery. A freshly generated output manifest is never evidence. **A modification therefore costs exactly one replay**: the PR run executes the changed pipeline in full; when the PR merges with a merge commit, its head is an ancestor of the main push, whose diff against that head is only whatever else landed on main meanwhile, so the push reuses it; later change sets compare against that run (discovery) or a re-pinned run. Limit: a squash or rebase merge makes the PR head unreachable from main, so that one main push has no candidate and replays once (merge commits, as this repository uses, avoid it). If main moved a pipeline's scope between the PR's test and the merge, the diff shows it and the replay is correct, not wasteful.
4. No file differs from the attested commit if it is in the pipeline's **static import closure** (from `entryModules` with `ast`; relative imports and every package `__init__` resolved; any dynamic import forces full), is referenced by a **string-literal path** in that closure (data directories, specifications, lock files), is a pipeline output or owned package, is a Python environment file (`.python-version`, `requirements-*`, `pyproject.toml`), or is an **existing data file** (modified/deleted non-Markdown paths under `data/` force full; *new* data files for a new stage do not).
5. No file outside the pipeline reads its runtime cache: a literal `.cache/stageNN` or an import of the cache-reader names (`arrays`, `restore`, …) from the pipeline's construction module. Stage47 evaluation reads the Stage46 sealed control bank, so the Stage47 readers are listed in `reviewedCacheConsumers` and the dependency is enforced by `cacheDependencies` (below). This is the fail-closed answer to a skipped reconstruction starving a later step.
6. The workflow still runs every command that passed in the attested run, with no new `if`/`continue-on-error` except the registered reuse gate (and Stage39's existing gate). Action bumps, extra steps and later stages do not matter; removed or newly conditioned validation forces full.
7. The runner matches the pinned runtime gate: Linux x86-64, Ubuntu 24.04, Python 3.12.2 and exact numpy 2.2.6, scipy 1.16.0, shapely 2.1.2, matplotlib 3.10.6. **The runner image revision is deliberately not gated** (Stage39's registry gates it, which makes reuse lapse each time GitHub updates the image). The attested log header was not retrievable in this session, so these are the pinned toolchain, not a copy of that log's image line. Manual full dispatch is the backstop for runtime drift. This is a conscious relaxation relative to Stage39, recorded in D081.
8. Edits to the selection machinery and policy files (`.github/validation/`, `scripts/validate/ci_*`, `AGENTS.md`, the workflow) are not pipeline dependencies, so they neither force a replay nor count as a pipeline change. They are guarded by the selector's own unit tests (always run, never replayed) and by rule 6: a change set that removes or newly conditions any validation step the attested run executed is full. A buggy selector is therefore caught by its tests before it can over-reuse, and manual full dispatch is available at any time to re-replay everything.

Anything unproved, unreadable, missing or failing yields `full`; the selection step is `continue-on-error`, so a crashed selector also yields full. Explain a selection with `python3 -m scripts.validate.ci_frozen --event pull_request --base <base-sha>` (add a token to see live candidates).

## Granularity: per pipeline, not per command

Reuse is decided per pipeline (Stage45 and Stage46 separately) and keyed on the byte contents of what the replayed commands can read, not on which commit last ran them. Per-command reuse inside a pipeline is deliberately not attempted: Stage46's evaluation and verification read the sealed 32,768-draw banks that only its construction produces, and those banks are uncommitted `.cache` files, so skipping construction while running evaluation is impossible without a persisted-bank cache (out of scope; AGENTS.md forbids adding inference caches without separate authorization). The cheap commands of each pipeline (diagnosis, priors, estimation, numerics, report, manifest, reference) are outside the expensive commands' import closure and always run, so editing a report/manifest module (`reportPaths`) or a document never triggers the expensive replay; editing a module that construction, evaluation or verification imports, or any input or output they reference, replays the whole expensive group once.

## Registering a pipeline, and Stage47

A pipeline is frozen by default once a main run has executed its commands successfully. To register one, add a registry entry (`entryModules`, `ownedPaths`, `outputPaths`, `extraDependencies`, cache reader names, `replacedCommands`, `integrityChecks`), gate its expensive commands with `if: steps.frozen.outputs.<name> != 'integrity'` and add the matching `Verify reused …` step, in the stage's own change set (which runs the new commands in full anyway, because no attested run has executed them); no pin is needed at registration because discovery reads the first successful full run (its own PR run) from the API; pin it afterwards (see *Durable attestations*). Stage47 (PR54) is registered: its replaced commands are `audits`, `construction`, `evaluation`, `attribution` and `verification` (the ones that read cached banks), gated like the others; its cheap commands (`pilot`, `prior`, `structure`, `structural_diagnostics`, `pair_widths`, `report`, `manifest`) always run. Stage47 reads the Stage45 bank (`audits`) and the Stage46 control bank (`evaluation`, `verification`), so its registry entry declares `cacheDependencies: [stage45, stage46]` and those pipelines list the Stage47 readers under `reviewedCacheConsumers`. `ci_frozen.select` applies the dependency: **whenever Stage47 runs in full, Stage45 and Stage46 run in full too**, so the caches exist; a reused Stage47 skips every command that reads them, so Stage45/46 may be reused independently. Its first attestation was the PR54 run itself, found by discovery and now pinned (see *Durable attestations*); that run replayed everything. Not a regression: with Stage45, Stage46 and Stage47 all in full the `python` job is roughly 2 hours, which is why its `timeout-minutes` is 180 (it was 150).

**Stage48 (candidate-balance scale comparison)** is registered the same way. Its replaced commands are `scripts.balance_scale.evaluation --check` (257 component seats at 32,768 draws for three restrictions plus the 193-seat composed supporting check; about 30 minutes) and `scripts.balance_scale.verification --check`; its cheap commands (`fit`, `decision`, `report`, `manifest`) always run. It writes and reads no runtime cache (`cacheReaderModules` is empty), imports only the Stage45/46/47 simulation, metric and coordinate helpers (never their cache readers), and so declares no `cacheDependencies`; editing any of those shared helpers puts Stage48 back to a full replay through its import closure. Its first attestation was the Stage48 PR run itself, found by discovery and now pinned.

**Stage54 (composed Monte Carlo precision)** is registered the same way. Its replaced commands are `scripts.composed_precision.evaluation --check` (the 193-seat composed bank over four 512-draw blocks for three restrictions, plus the nine representative seats over four more blocks and three layer-only replicates; about 45 minutes wall on 4 local cores, parallel over independent election and block tasks; 2 hosted cores would take up to about twice that) and `scripts.composed_precision.verification --check` (re-simulates two seat-blocks); its cheap commands (`decision`, `report`, `manifest`) always run. ## Durable attestations (2026-10-06, D100)

**Invariant:** a successful full run that executed every replaced command of a pipeline remains reusable indefinitely while that pipeline's code, consumed inputs, outputs and hashes, environment and dependency closure are unchanged. Newer unrelated runs, reuse-only runs and the number of runs since never retire it.

**What went wrong.** Discovery read only the newest `maxRuns = 10` successful runs. A reused (`integrity`) run correctly is not an attestation, so after ten further successful runs Stage47's only genuine attestation (PR #54, run 37412099846) fell outside the window. The old global seed (`d0fa5a66`) predates Stage47 and cannot attest it, so Stage47 went full, and because Stage47 declares `cacheDependencies: [stage45, stage46]`, Stage45 and Stage46 were forced full too, replaying roughly 1.5 to 2 hours (Stage45 about 5 minutes, Stage46 about 41, Stage47 about 62) on unrelated and even docs-only PRs. Stage48 (run 37434895393) and Stage54 (run 37452017775) were next to drop out. Raising `maxRuns` would only have postponed this.

**Selection, per pipeline.**
1. **Pin, Git-only.** `pipelines.<name>.pin` records the commit, run id and URL, creation time, an evidence file (`.github/validation/evidence/frozen-run-<id>.json`: the run, its python job and every step with conclusion and timestamps) with its SHA-256, and a **scope fingerprint**: SHA-256 over the git blob ids of everything a replay can read (the static import closure, referenced literal paths, owned and output paths, extra dependencies, Python environment files) at the pinned commit. The pin is used when its evidence is unchanged and shows every replaced command `success`, the recorded steps are all still in the workflow ungated, and the whole Git proof above holds, including that the fingerprint of the current tree equals the recorded one (so a pin recorded against the wrong commit or scope is refused). No API call is made.
2. **Discovery, only if the pin does not prove reuse** (pin stale, evidence changed, or no pin). One lazy walk over `workflows/ci.yml/runs?status=success`, newest first, paginated (`perPage`, at most `maxPages`), shared across pipelines. Runs that are not push or manual dispatches of `main`, or pull-request runs, are ignored; runs whose head commit is not an ancestor of the tree under validation cost no job request; every other run costs one job request, capped at `maxJobFetches`. The **newest run whose python job executed every replaced command** of this pipeline wins (reuse-only runs are skipped because their replaced steps were skipped); the walk stops at the pinned run or at either cap. The chosen run must then pass the same Git proof. Manual `workflow_dispatch` runs of main count as attestations (they run everything), which also makes a full dispatch a one-step way to re-attest.
3. **Failure is closed.** API error, malformed response, missing token or an exhausted bound yields no discovered candidate: the pipeline uses its valid pin if that proved reuse (step 1), otherwise runs full. A stale pin together with an API failure is full.

Unchanged: the dependency closure, referenced-path, existing-data, environment, dirty-tree, unreachable-commit, unreviewed-cache-consumer and workflow rules; the pinned runtime gate; `cacheDependencies` (Stage47 full forces Stage45 and Stage46 full; an unchanged Stage47 selects `integrity` and forces nothing); manual dispatch is full; no statistical check, tolerance, contract or output is touched.

**Logs.** The selector prints one line per pipeline, for example `stage47: integrity - reusing the pin attestation 22662219 run 37412099846: dependency scope unchanged since that full run (44 files in closure, 86 changed paths outside it)`, or for a replay `stage47: full - pin attestation 22662219 run 37412099846: dependency changed: scripts/... | no full run newer than the pinned run among 12 reachable runs examined`, followed by the JSON summary (`chosen` carries source, commit, run id and URL). When discovery supplies the attestation the line also says why the pin was not used.

**Current pins** (each verified from the run's actual python-job steps: every replaced command executed with conclusion `success`, with the multi-minute timings a real replay has): Stage45, Stage46 and Stage47 to PR #54 run 37412099846 (head `22662219`; Stage45 construction 3m31s, Stage46 construction 35m, Stage47 construction 47m and attribution 13m); Stage48 to PR #64 run 37434895393 (head `2a000a11`; evaluation 13m); Stage54 to PR #66 run 37452017775 (head `49f296a1`; evaluation 64m). Stage63 to the Verify run of main at the merge of PR #91, run 37573315688 (head `e0bc9560`; its bounded `evaluation --check` replay and `verification --check` executed with conclusion `success`; the first full Stage63 run, which also attests PR run 37564308018). The older `.github/validation/evidence/frozen-main-d0fa5a66.json` is kept as a historical record and no longer referenced.

**Refreshing a pin.** Never required for correctness: after a legitimate pipeline change, the replaying PR's run is the newest full run, so discovery selects it automatically (a pin is only a durable fallback that makes reuse independent of the API and of run counts). To refresh the pins a later maintenance PR runs, with a token, `python3 -m scripts.validate.ci_frozen --record-pin RUN_ID [--pipeline stageNN]` in a checkout whose HEAD contains the run's commit; it reads the run and its python job, refuses any pipeline whose replaced commands did not all succeed in that run, writes the evidence file, fingerprints each scope in a temporary worktree at the run's own commit and rewrites the registry pins. `python3 -m scripts.validate.ci_frozen --fingerprint --pipeline stageNN` prints the current scope fingerprint. A pin is never edited by hand, never invented, and a pipeline without a verified full run simply has no pin and is discovered or full.

**Cost of this change.** It touches only the selector, its tests, the registry and evidence files, documents and a handoff fragment, all of which are outside every pipeline's closure, so its own pull request reuses Stage45, 46, 47, 48 and 54 from their pins (checked locally against the real registry). Stage39's separate, older path still runs its five commands because `.github/` and tests changed.

**Stage63 (layer-replicated composed simulation)** is registered the same way. A complete replay is about 6 CPU hours (nine representative seats with 64 layer replicates each on all 4,096 national draws, plus a nine-seat win panel with 8 replicates; about 1.6 hours on 4 local cores, longer than the hosted job limit on 2 cores), so the replaced `scripts.layer_replication.evaluation --check` is a bounded replay: it regenerates two replicate banks of every seat (36 banks, about 40 CPU minutes, parallel and independent of the worker count) and compares each, to the artifact tolerance, with its stored record; `scripts.layer_replication.evaluation --check --full` replays every replicate and was run locally. The other replaced command, `scripts.layer_replication.verification --check`, re-simulates two replicate banks without the exact solve reuse and re-derives the decision arithmetic with plain loops; its cheap commands (`decision`, `report`, `manifest`) always run and re-derive every statistic from the stored records. The pipeline writes and reads no runtime cache, imports the Stage54 stream/simulation helpers (so editing Stage54 or any Stage45 to Stage48 helper it imports puts Stage63 back to a replay through its import closure), and reads the Stage54 `evaluation.json` as a pinned input. The hardware-dependent `timing.json` is compared by structure only. There is no pinned seed: its first attestation was the Stage63 PR run, and it is now pinned (see *Current pins*).

## New sources: do not append to `data/sources.json`

Reuse selection cannot make an edit to `data/sources.json` cheap, because the failure is not in selection. About 25 historical stages (Stage21 onward, including Stage45 and Stage46) list the whole file's SHA-256 under `priorDataHashes` in their `preservation.json`/`prior-data-contract.json`, and their always-run `--check` steps compare it. Measured on this branch: appending one record to `data/sources.json` makes `scripts.uncertainty_revision.manifest --check` fail with `Changed prior artifact: data/sources.json`. The registry has not changed since Stage21, and changing it would mean editing frozen contracts or replaying every stage.

So: acquisitions made from now on (MMP legislation text, 2026 polls, the nomination snapshot, ...) go in a new standalone registry file with the same `schemaVersion: 1` schema, validated by the same `SourceRegistrySchema` (Stage40's `data/processed/forecast-readiness/source-registry.json` is the precedent), and new code reads that file directly. New files outside every pipeline's closure, new Python tests, new TypeScript and docs do not change either frozen pipeline's selection, so those PRs run unit tests and the new stage's own checks, with Stage45/46 at integrity level. The older Stage39 path is blunter: any change under `scripts/tests/`, `.github/` or an unreviewed path makes the five Stage39 commands run (about 4 minutes), and Stage39 always replays on main pushes.

## Job limits, process-time guards and permissions

`check` has `timeout-minutes: 20` and `python` has `timeout-minutes: 180` (a fully executed run was about 60 minutes before Stage47; the first Stage47 run executes everything, roughly 2 hours), so a runaway step fails instead of burning the six-hour default. Permissions stay read-only (`contents: read`, `actions: read`). **Do not put machine-speed or wall/CPU-time gates (`time.process_time()` budgets and the like) inside `--check` reconstructions:** they fail on slower runners without any statistical meaning (Stage47's frozen 40-minute CPU guard is the observed case). Bound runaway cost with `timeout-minutes`, not with a gate that changes scientific outputs.

## Consequences and limits

- **This change set itself reuses Stage45/46**: the Git diff against the attested commit `d0fa5a66` touches only CI/selector files, tests, documentation and the workflow; no file in either pipeline's closure, no data file and no pipeline output differs, and the same selector tests that gate it always run. Stage39's own, older path still sees a `.github/` change and replays its five commands (about 4 minutes). An optional manual `workflow_dispatch` of Verify is the full replay and is not required for this change set.
- Expected cost afterwards for a change that leaves Stage45/46 and their closure unchanged: roughly the unit-test and other historical-pipeline time, not 90+ minutes. A change that adds a new stage still pays that stage's own cost once. Until PR54 removes its dependence on the Stage46 bank, Stage46 stays full there and only Stage45 (about 4.5 minutes) is saved.
- Reuse relies on a prior successful Linux run plus unchanged bytes. It does not recompute the sealed 32,768-draw banks, which are uncommitted `.cache` files; there is nothing cheaper than regeneration to check them. Dynamic path construction invisible to static analysis and non-Linux runtimes are covered by the full runs that follow any modification and by manual dispatch, not by this check.
- Node 24: `actions/checkout` v5, `actions/setup-node` v5 and `actions/setup-python` v6 (all `using: node24`; newer majors exist but were not needed). Behaviour-relevant inputs (`fetch-depth: 0`, `node-version-file`, `python-version-file`, `cache: npm`) are unchanged.
- No inference cache, schedule, benchmark run or statistical change. PR concurrency and event triggers are unchanged.
- The frontend `check` job has a guarded step that runs `npm run check:dist` (production build must not contain synthetic fixture content) once that script exists in `package.json`, and is skipped with a message until then. It runs after `npm run check`, which builds `dist`.

# Parallel full replay (2026-10-10)

**Why.** The Verify `python` job has `timeout-minutes: 180` (a runaway guard set when Stage47 made a fully executed run about 2 hours; see *Job limits* above). With Stage45, 46, 47, 48, 54 and 63 all replayed in one job, a manual `workflow_dispatch` of Verify, the explicit full gate, now exceeds that cap (PR #95 was cancelled at 3 hours when a new workflow file forced the full replay). GitHub's own limit is 6 hours per job, so the cap is ours, not GitHub's.

**What.** `.github/workflows/full-replay.yml` ("Full replay", `workflow_dispatch` only) runs the same commands as the Verify `python` job as parallel matrix jobs, plus the frontend `check`, with no reuse and no selection step. The command list is not copied: `scripts/validate/ci_full_replay.py` reads it from `ci.yml` and runs one group in workflow order, ignoring `if:` gates and skipping the named reuse steps. Groups: `stage39` (candidate integration), `stage45-47` (one job, because Stage47 reads the Stage45 and Stage46 banks that their constructions write earlier in the same job), `stage48`, `stage54`, `stage63`, and `base` (everything else, including the full unittest discovery and source validation). A final `Full replay passed` job requires every job to succeed.

**Guards.** `python3 -m scripts.validate.ci_full_replay --check` (run by every group, and by `scripts/tests/test_ci_full_replay.py` in standard discovery) fails if a `ci.yml` command would be lost or duplicated or a group is empty; the test also requires every registered pipeline's `replacedCommands` to sit in a non-base group (so a newly registered stage must be given its own group and matrix entry rather than silently lengthening `base`), keeps the workflow's group list equal to the script's, and requires the workflow to stay manual-only and unnamed in `ci.yml`.

**Unchanged.** `ci.yml`, the pull-request/main-push selectors, the registry and every pin. Verify's own manual dispatch still exists but is now the slow single-job path; use Full replay for the pre-release gate. A Full replay run is **not** an attestation to the discovery walk, which reads only `ci.yml` runs' `python` job; the durable pins and pull-request runs keep attesting. `full-replay.yml` is listed in `NON_VERIFY_WORKFLOWS` in `ci_frozen.py` (with `poll-refresh.yml`) so adding it does not force a frozen replay on its own PR.

**Timeouts are estimates.** Per-group limits (base 150, stage39 45, stage45-47 270, stage48 120, stage54 180, stage63 120 minutes) are set from the durations recorded above and not yet measured on this workflow; each group writes a per-command timing table to its job summary, and the first run should be used to tighten them.
