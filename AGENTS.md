# Persistent project rules

- GitHub (`jamesfeng24/nz-election-model-2026`) is the canonical project state. Local conversations are not a source of truth.
- Before every scoped task, read AGENTS.md, PROJECT_STATE.md and any pending fragments in `handoff.d/` (the newest PROJECT_STATE entry, possibly still in a fragment, holds the authorized scope, agreed sequence, open questions and exact next action). For CI, validation or handoff-process work also read docs/ci-validation.md; for roadmap or sequencing questions read the Active roadmap in docs/stage39-forecast-roadmap.md. Read DECISIONS.md, METHODOLOGY.md, DATA_SOURCES.md and docs/statistical-specification.md before a new modelling component, at integration checkpoints, for relevant methodological/provenance questions, or when PROJECT_STATE.md directs it. Routine ingestion need not reread unchanged unrelated documents. Inspect only relevant code. Inspect git status and synchronize safely before editing. Preserve other contributors' work.
- For new work, briefly inspect and plan before implementation. For resumed work, inspect saved/local state and continue the existing plan; do not repeat ceremonial planning language or redo discovery unnecessarily. Use a concise checklist/state handoff when useful; no specific planning tool such as TodoWrite is required.
- Additional agents are optional: use them only for independent, bounded work where parallelism clearly helps, never merely because a task is called complex.
- Historical compatibility and explicit preservation requirements take precedence over generic advice to delete old code or avoid compatibility paths. Do not remove validated historical parsers, data or contracts unless that replacement is explicitly authorized.
- Raw CSV/TSV application/data-pipeline inputs are not spreadsheet-authoring tasks. Do not invoke workbook workflows merely because election sources use `.csv`; spreadsheet tooling applies only to requested spreadsheet/workbook deliverables or spreadsheet-style analysis. Routine code/schema/data inspection needs no visualization unless explicitly requested or materially useful; use prose/tables when clearer.
- Once a scoped task is authorized, continue routine reversible implementation decisions without approval stops. Ask only when missing information materially affects correctness/scope or an irreversible/external action requires user authorization. Investigate and attempt a bounded resolution before stopping; stop only for required user input, unresolved correctness risk or actions outside authorization. Investigate and document unexpected source discrepancies rather than automatically stopping; preserve explicit prior-data protection and stage boundaries.
- Preserve raw source data unchanged. Record provenance and checksums before processing.
- Processed datasets must be reproducible through documented scripts.
- Do not invent missing political or statistical data. Synthetic fixtures must be explicitly labelled and kept out of application results.
- Expose uncertainty rather than fake precision. Missing values are not zero.
- Avoid double-counting overlapping statistical effects. Record each effect's estimand and dependencies.
- Keep a static/client-side architecture: React, TypeScript, Vite, Vitest; no backend or database.
- At intermediate checkpoints, run checks relevant to changed code. Retain substantive data validation, checksum/provenance checks, deterministic regeneration, prior-output compatibility checks and final-stage verification. Run full configured checks at final readiness where applicable under the scoped rules below. Run relevant Python tests and source/data validation for ingestion changes. Run `npm run test`, `npm run typecheck` and `npm run build` when frontend/shared TypeScript changes, at major integration/model-release checkpoints, or when explicit current task instructions require them before a PR. Do not repeat unrelated frontend checks for Python-only checkpoints. Run configured formatters/linters relevant to changed code; document unavailable tooling. Fix failures or record precise blockers; never claim unrun checks passed.
- Treat each meaningful checkpoint as potentially the last before a usage cutoff. Update PROJECT_STATE.md with the completed unit, important counts/state, unresolved issues and exact next action, then make a resumable local commit. Routine local checkpoints do not require a push or hosted CI run. Push at the review/final-validation checkpoint, or when the user requests a remote handoff. Keep an explicit distinction between locally committed and remotely preserved work; verify the remote after each authorized push and never force-push shared history. Raw acquisition remains checkpointed before transformation.
- Update PROJECT_STATE.md at the end of every stage, including exact next task and check status. Update decisions, methodology, sources and changelog when affected.
- Do not start later stages unless explicitly asked. Current authorized scope is recorded in PROJECT_STATE.md; never infer permission for later stages.
- When interrupted, record incomplete work, commands, branch, blockers and next action in PROJECT_STATE.md. A fresh session must resume from files alone.

## Materiality and usage discipline

- Hosted verification runs on pull requests and pushes to main, not standalone feature-branch pushes. Workflow/event/PR-or-ref concurrency cancels superseded runs on the same PR/ref; unrelated PRs/workflows remain separate. Newer main commits may supersede older main runs, and the latest main commit receives the complete gate except that a frozen pipeline proven unchanged since an attested full main run may be reused (Bounded validation reuse; docs/ci-validation.md); manual `workflow_dispatch` is always the complete gate. Unskipped PR updates still run CI; this is not one run per stage.
- Intermediate resumable checkpoints may use `[skip ci]` after relevant local checks pass. Such heads are not merge-ready; skip markers can leave required checks pending. Final review heads and merge commits must have no skip marker and must pass the full required checks on the exact SHA. Never put markers in PR titles or default squash/merge messages. Do not rewrite existing commits, disable protection, remove checks or mark unrun checks successful. Avoid dispatching duplicate benchmark workflows; retain the full Ubuntu/Python/frontend/source/reproduction/preservation gate. Cache improvements are separate work.

- Work repository-first and offline-first: exhaust preserved sources and existing derived evidence before external research. Before extended source archaeology, acquisition, reconciliation or precision refinement, ask whether resolution could materially change model selection, coefficients, validation, vote shares, winner probabilities or downstream uncertainty.
- Where possible bound the downstream effect and compare it with dominant uncertainty at the relevant stage. Preserve and propagate immaterial uncertainty rather than pursuing extra decimals or unknowable microdata. Do not assume future forecast uncertainty has already been measured.
- Correctness problems—leakage, corrupt IDs, wrong electoral rules, conservation/contract failures, material bias or changed conclusions—require investigation. Already valid bounded numerical/source uncertainty is a precision question, not automatically a correctness failure. Never zero-fill missingness, choose arbitrary midpoints, invent identities or weaken tests/tolerances to save usage.
- If external research is necessary, define the precise missing fact and perform one bounded authoritative search/acquisition pass. Checkpoint useful sources promptly. Repeat only when materially consequential evidence could emerge; otherwise document the limitation and continue with the strongest defensible evidence.
- Invest substantial effort in reusable statistical infrastructure, deterministic algorithms, uncertainty propagation, backtesting, candidate-history machinery, Monte Carlo/MMP architecture and correctness tests when authorized. Materiality discipline is not permission to simplify foundational correctness away.
- Run focused checks during implementation and complete required final verification once, repeating only when failures or subsequent relevant changes justify it. Keep useful checkpoints committed locally; push at review readiness or an explicitly requested remote handoff.
- For later authorized NAT/LAB elasticity, parameterize the retained baseline transformation in one reusable pipeline. If conclusions are materially invariant across transforms, record that and stop refining this sensitivity; if not, preserve and investigate the consequential difference. This rule does not authorize starting that stage.

## Bounded validation reuse

- Ordinary PR validation may use only reviewed dependency-aware historical reuse; unknown/new tests, dependency or shared-code changes, CI/registry changes and missing comparison history fail closed to full validation. All behavioural Python tests remain mandatory.
- Stage39 and the frozen pipelines Stage45, 46, 47, 48 and 54 currently have explicit previously successful Linux attestations (Stage39 `.github/validation/stage39.json`; the frozen pipelines `.github/validation/frozen-pipelines.json`, each with a durable pinned full run, see the next rule); all other historical pipelines continue full checks. Frozen-pipeline PR reuse is Git-proved against the attested commit (import closure, referenced paths, outputs, environment, unchanged existing data, no unreviewed reader of the pipeline's runtime cache); only their expensive `--check` commands (the registry's `replacedCommands`) are replaced, while their cheap diagnosis/estimation/decision/report/manifest checks always run. A later stage that reads a registered pipeline's cache keeps that pipeline full until reviewed. New registrations need an observed successful full Linux main run. Pure archival reproduction tests may be classified semantically in `.github/validation/test-semantics.json`, but no tests are currently omitted. Standard unittest discovery remains the full suite.
- **Frozen stages skip replay; modified stages replay once.** A registered frozen pipeline's expensive `--check` replay is skipped while its code, consumed inputs and hashes are unchanged; whenever any of them is modified it runs in full once, on the PR that modifies it; that successful PR run is itself the reference (PR and main runs both attest), so the merge's main push and later changes reuse it with no registry edit. Reuse is per pipeline, not per command. Manual `workflow_dispatch` always runs full. Pull-request and main-push reuse needs the Git proof in docs/ci-validation.md; anything unproved is full. Edits to the selector, registry or this file do not force a replay; they are guarded by the always-run selector tests and by the rule that attested validation may not be removed or newly conditioned. Every new stage registers its expensive checks the same way and is frozen after its first green main run. Do not put machine-speed/CPU-time gates in `--check`; bound cost with job `timeout-minutes`.
- **Frozen-pipeline attestations never expire (D100, 2026-10-06).** A successful full run that executed every replaced command of a pipeline stays reusable indefinitely while that pipeline's code, consumed inputs, outputs, environment and dependency closure are unchanged; newer unrelated runs, reuse-only runs and run-count windows never retire it. Each registered pipeline carries a durable **pin** in `.github/validation/frozen-pipelines.json` (commit, run id, evidence file hash, scope fingerprint), verified from the run's actual job steps and checked first from Git alone (no API call). Only when the pin does not prove reuse does the selector walk the successful, reachable Verify runs through the Actions API, per pipeline and paginated, skipping reuse-only runs (never an attestation) and stopping at the pinned run; an API failure falls back to the valid pin, otherwise to full. A pipeline's first full run (its own PR) is found by that discovery with no registry edit; a later maintenance change may pin it with `python3 -m scripts.validate.ci_frozen --record-pin RUN_ID`, which is never required for correctness. Pin only verified full runs; never invent or guess one. Every fail-closed rule is unchanged (changed dependencies, inputs or environment, unreachable commits, dirty trees, unreviewed cache consumers, removed or newly conditioned validation, `cacheDependencies`).
- **`data/sources.json` is frozen; add new sources to a standalone dated registry.** About 25 historical stages hash the whole file as a preserved prior artifact (e.g. `data/processed/uncertainty-revision/preservation.json`), so appending even one record fails their cheap `--check` preservation step in every CI run, whatever CI scoping selects. Record new acquisitions (MMP legislation, 2026 polls, nominations, ...) in a new standalone registry of the same schema, as Stage40 did in `data/processed/forecast-readiness/source-registry.json`, and have new code read it directly. Never edit `data/sources.json` or the historical contracts' pinned hashes.
- Do not use a newly generated output manifest as proof of a prior passing run, silently weaken checks, add inference caches or rerun national MCMC for CI. See `docs/ci-validation.md`.

## Multi-assistant handoff (Claude and ChatGPT alternate)

- Either assistant must be able to resume from the repository alone. Use no assistant-specific tooling or chat memory as a source of truth; record anything that matters in PROJECT_STATE.md, DECISIONS.md, the stage docs, CHANGELOG.md or METHODOLOGY/DATA_SOURCES as affected.
- Keep PROJECT_STATE.md entries newest-first and in the existing shape: dated heading "StageNN … — date", branch and important commits/PRs, what changed and what did not, counts, exact check results (never claim unrun checks), limits, local-versus-pushed status, **exact next action**, exact reproduction commands and logs. Keep full hashes where earlier entries do.
- Work in tightly bounded, **one-question stages**: a frozen pre-registered design committed before scoring, an explicit "do not" list, a plan proposed first and signed off by the user before implementation threads run, and no later stage started without explicit authorization. Do not reopen decided questions (see the authorized-scope paragraph and do-not-reopen list in PROJECT_STATE.md) or rerun/regenerate frozen stages whose code, inputs and hashes are unchanged.
- Threads never merge pull requests. The CI-scoping PR itself is merged only by the user (James, who uses this account). After it merges, the user has given standing permission (2026-10-06) that (a) running or dispatching Verify, including a full manual dispatch of main, needs no further permission, and (b) completed major-stage PRs are reviewed and, where appropriate, merged by the project coordinator session (Opus 5.5, not a thread), which then returns to the user with an interpretation of the results and recommended next steps. Any merge outside that standing permission, and every later-stage start, still waits for the user. Ordering constraints recorded in PROJECT_STATE.md (for example CI scoping merges before the Stage47 repair PR) are binding.
- **Shared handoff documents are updated by fragments, never by PRs directly** (standing rule, 2026-10-06). CHANGELOG.md, PROJECT_STATE.md, DECISIONS.md, METHODOLOGY.md, DATA_SOURCES.md and the roadmap status table are edited by every PR, so parallel PRs conflicted on them and each conflict cost a CI re-run. A PR therefore **does not edit those documents**; it writes one fragment, `handoff.d/YYYY-MM-DD-<stageNN-or-area>.md`, with optional sections introduced by `<!-- fold: changelog|state|decisions|methodology|sources|roadmap -->` (format and placement rules: `scripts/fold_doc_fragments.py` and `handoff.d/README.md`; omit a section instead of writing "no change"). Stage-specific documents (a stage's own `docs/*.md`, the export contract, and so on) are still edited in the PR. The duties above to update PROJECT_STATE.md, the changelog, decisions, methodology and sources are met by writing the fragment; a PR description still lists each handoff document as folded-by-fragment or "no new".
  - After a batch of concurrent PRs has merged, the coordinator folds every pending fragment in one docs PR (`python3 -m scripts.fold_doc_fragments`, validate first with `--check`); that fold deletes the fragments and leaves the shared documents as the full record. A thread folds only when told to.
  - Unfolded fragments on main are part of the handoff record: a fresh assistant reads `handoff.d/` together with PROJECT_STATE.md, since the newest entries may still be in fragments.
  - Decision numbers still come from the coordinator and are written in the fragment's `decisions` section.
  - The frozen-pipeline selectors treat `handoff.d/*.md` as documentation, so fragment-only changes never force a replay or full validation.
- **Batching threads.** Start a new thread only from main after the current batch of PRs has merged, unless its work is independent of the open PRs. A thread that has not finished its PR can see the updated main; a thread started earlier on a stale base cannot. Several unrelated PRs open at once is what made the shared documents conflict.
- Record a new standing rule in this file in the same change that introduces it, and any substantive decision as the next D-number in DECISIONS.md.

## Pull requests

- **Title:** `StageNN: <lowercase-initial phrase naming the one bounded question or result>` for numbered stages (for example `Stage47: repair Gaussian expectations and audit uncertainty widths`). For non-stage work use `<Area>: <lowercase-initial phrase>` with a short area such as `CI:`, `Roadmap:` or `Docs:`. No skip markers, no ids, no assistant or model names. Stage branches are `stage/NN-kebab-name`.
- **Body**, plain prose, in this order. Any required attribution lines stay first. `## Scope` (the one bounded question or change, frozen checkpoint commits, what is preserved, what is explicitly not done). `## Findings and recommendation` for stages, or `## Changes and limits` / `## Decisions recorded` for non-stage work, with the headline numbers and limitations stated, never fake precision. `## Local validation` as a bullet list of checks actually run, with counts, and what was not run and why. `## CI and boundaries` (what hosted runs mean for this PR, skips, known limits). `## Final published head and hosted validation` (exact head SHA, link to the Verify run on that SHA, which jobs passed, durations; say plainly if a run failed or is pending). Close with the next separately authorized task and whether the PR is to be left unmerged.
- **Decision numbers** come from the coordinator, not from taking the next number on main: parallel PRs collide.
- Describe what the change does and its evidence, not the process. Do not claim unrun checks passed. Update the body when the head or run status changes.
