## CI: Publish workflow, 2026-10-10

- New `.github/workflows/publish.yml` ("Publish") turns the newest merged poll refresh into a published forecast: `weekly_refresh.adopt` in the runner, development gate, full production run (65,536 draws, Python publication gate), TypeScript release gate and append-only archive, static site build, independent archive and tree checks, then a push of the built site, the `forecasts/` archive and a **frozen copy of the whole site for that week** (`archive/<data cutoff date>/`, written once, never rewritten by a later publish) to the public site repository. Any failed gate stops it before anything is pushed. It starts on a push to main that changes a refresh index or the site code, or manually.
- A new forecast and archive entry are made only when the refresh brought new national polls (a new data cutoff: id `nowcast-<cutoff>`); with no new polls a publish is site-only (the live root rebuilt from the current site code and the existing archive; no new entry, no frozen copy touched, no commit if nothing differs). Corrections (`-r2`) are manual and rebuild only their own week's frozen folder. Details: `docs/publish-workflow.md`.
- Nothing is pushed without an explicit go: a manual run needs the publish box ticked, a push-triggered run needs the repository variable `PUBLISH_AUTO` to be exactly `true`, and both need main. Every other run is a dry run that never contacts the public repository or uses the token. Public commits are authored and committed by James with a plain message and no trailers; nothing is force-pushed.
- New package `scripts/publish_workflow/` (`plan.py` mode, release/site-only decision, ids, options; `verify.py` independent checks; `public.py` the only code that touches the public repository; `public-README.md`), 57 tests in `scripts/tests/test_publish_workflow.py` (the push is tested against a local bare repository), the workflow added to `NON_VERIFY_WORKFLOWS` in `ci_frozen.py` (so editing it forces no frozen replay), the specification, release checklist (item 16) and Stage70 text updated. No model, statistical code, data, configuration or frozen-pipeline change; `ci.yml` and its 180-minute timeout are unchanged.

## D130 — 2026-10-10 — the Publish workflow adopts the newest refresh and publishes; nothing is pushed without an explicit go

James decided on 2026-10-10 that merging the weekly poll-refresh pull request is his only manual step: a GitHub Actions workflow (`.github/workflows/publish.yml`) adopts the newest refresh (`weekly_refresh.adopt`) in its runner, reruns the forecast, runs every release gate and pushes the built site and forecast archive to the public site repository, with a failed gate stopping it before anything is pushed. This replaces keeping adoption manual for the weekly chain; the refresh routine itself still never edits the configuration (Stage70). Alternatives rejected: committing the adoption straight to main (shared history is never pushed to directly) and leaving adoption manual (a second manual step each Monday). The runner's adoption reaches main later through a bookkeeping pull request, so main's configuration can trail the published forecast until that is merged. The first publish and every later one needs an explicit go: a manual run with the publish box ticked, or the repository variable `PUBLISH_AUTO=true` that James sets after approving the first publish. Public commits carry James's identity, a plain message and no trailers. Number provisional (allocated by the coordinator).
